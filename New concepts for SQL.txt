LAST_INSERT_ID()  -- MySQL
SCOPE_IDENTITY()  -- SQL Server / SSMS

What SCOPE_IDENTITY() actually does
It returns the ID generated by the most recent INSERT in the current session. That is all it does. It has no memory of older inserts.
So if you insert a new user and immediately call SCOPE_IDENTITY(), it gives you that new user's ID. But if you want the ID of user 25 who was inserted earlier, SCOPE_IDENTITY() is useless there.

INSERT INTO users(name, email, gender, date_of_birth, salary)
VALUES ('Uj', 'uj@gmail.com', 'Male', '2001-07-05', 54000);

-- Right after, insert address for the user just created above
INSERT INTO addresses(user_id, street, city, state, pincode)
VALUES (SCOPE_IDENTITY(), 'Vishwas Nagar', 'Delhi', 'Delhi', '110032');

Difference between the syntax of MySQL and SSMS

=======================================================
MySQL vs MS SQL Server (T-SQL) -- SYNTAX DIFFERENCES
=======================================================

SSMS = SQL Server Management Studio
      It is just the GUI tool (like MySQL Workbench is for MySQL).
      The actual database is Microsoft SQL Server (MSSQL).
      The query language SQL Server uses is called T-SQL (Transact-SQL).

The core concepts are identical in both:
SELECT, INSERT, UPDATE, DELETE, JOIN, GROUP BY, WHERE, etc.
The DIFFERENCES are in specific syntax, functions, and keywords.

=======================================================
SIDE BY SIDE COMPARISON
=======================================================

-------------------------------------------------------
1. Limiting rows returned
-------------------------------------------------------

    MySQL:
    SELECT * FROM users ORDER BY salary DESC LIMIT 10;

    SQL Server (T-SQL):
    SELECT TOP 10 * FROM users ORDER BY salary DESC;

    -- SQL Server also supports ANSI standard syntax (2012+):
    SELECT * FROM users ORDER BY salary DESC
    OFFSET 0 ROWS FETCH NEXT 10 ROWS ONLY;

    Key difference:
        MySQL  -- LIMIT goes at the END of the query
        T-SQL  -- TOP goes right after SELECT at the BEGINNING

-------------------------------------------------------
2. Auto increment
-------------------------------------------------------

    MySQL:
    CREATE TABLE users (
        id INT AUTO_INCREMENT PRIMARY KEY
    );

    SQL Server (T-SQL):
    CREATE TABLE users (
        id INT IDENTITY(1,1) PRIMARY KEY
    );

    IDENTITY(1,1) means: start at 1, increment by 1.
    IDENTITY(100,5) would start at 100 and go 100, 105, 110...
    AUTO_INCREMENT in MySQL always starts at 1 by default
    (you change it with ALTER TABLE users AUTO_INCREMENT = 1000).

-------------------------------------------------------
3. String concatenation
-------------------------------------------------------

    MySQL:
    SELECT CONCAT(first_name, ' ', last_name) AS full_name FROM users;

    SQL Server (T-SQL):
    SELECT first_name + ' ' + last_name AS full_name FROM users;
    -- SQL Server 2012+ also supports CONCAT():
    SELECT CONCAT(first_name, ' ', last_name) AS full_name FROM users;

-------------------------------------------------------
4. String length function
-------------------------------------------------------

    MySQL:
    SELECT LENGTH(name) FROM users;

    SQL Server (T-SQL):
    SELECT LEN(name) FROM users;

    Same result, different function name.

-------------------------------------------------------
5. Current date and time
-------------------------------------------------------

    MySQL:
    SELECT NOW();        -- date + time
    SELECT CURDATE();    -- date only
    SELECT CURTIME();    -- time only

    SQL Server (T-SQL):
    SELECT GETDATE();    -- date + time
    SELECT GETDATE();    -- no separate CURDATE(), cast it:
    SELECT CAST(GETDATE() AS DATE);   -- date only
    SELECT CAST(GETDATE() AS TIME);   -- time only

-------------------------------------------------------
6. Quoting identifiers (table/column names)
-------------------------------------------------------

    MySQL:
    SELECT `name`, `email` FROM `users`;
    -- uses backticks for identifiers

    SQL Server (T-SQL):
    SELECT [name], [email] FROM [users];
    -- uses square brackets for identifiers

    Both: quoting is optional when the name has no spaces or reserved words.
    Required when column/table name is a reserved word or has spaces.

-------------------------------------------------------
7. Stored procedures
-------------------------------------------------------

    MySQL:
    DELIMITER $$
    CREATE PROCEDURE GetUsers()
    BEGIN
        SELECT * FROM users;
    END $$
    DELIMITER ;

    CALL GetUsers();

    SQL Server (T-SQL):
    CREATE PROCEDURE GetUsers
    AS
    BEGIN
        SELECT * FROM users;
    END;

    EXEC GetUsers;
    -- or
    EXECUTE GetUsers;

    Key differences:
        MySQL  -- needs DELIMITER change, uses BEGIN...END, called with CALL
        T-SQL  -- no DELIMITER needed, uses AS BEGIN...END, called with EXEC

-------------------------------------------------------
8. IF statement inside procedures
-------------------------------------------------------

    MySQL:
    IF salary > 50000 THEN
        SET result = 'High';
    ELSE
        SET result = 'Low';
    END IF;

    SQL Server (T-SQL):
    IF salary > 50000
        SET @result = 'High';
    ELSE
        SET @result = 'Low';
    -- No END IF in T-SQL

-------------------------------------------------------
9. Variables
-------------------------------------------------------

    MySQL:
    DECLARE v_salary INT;           -- inside a procedure
    SET v_salary = 50000;

    SET @session_var = 50000;       -- session variable, usable anywhere

    SQL Server (T-SQL):
    DECLARE @salary INT;            -- always uses @ prefix
    SET @salary = 50000;
    -- or
    SELECT @salary = salary FROM users WHERE id = 1;

    Key difference:
        MySQL  -- local variables (no @), session variables (with @)
        T-SQL  -- ALL variables use @ prefix, declared with DECLARE

-------------------------------------------------------
10. ENUM data type
-------------------------------------------------------

    MySQL:
    gender ENUM('Male', 'Female', 'Others')
    -- built-in data type

    SQL Server (T-SQL):
    -- No ENUM type. Use CHECK constraint instead:
    gender VARCHAR(10) CHECK (gender IN ('Male', 'Female', 'Others'))

-------------------------------------------------------
11. SHOW commands (MySQL-only)
-------------------------------------------------------

    MySQL:
    SHOW TABLES;
    SHOW DATABASES;
    SHOW INDEXES FROM users;
    SHOW PROCEDURE STATUS WHERE db = 'mydb';
    SHOW CREATE TABLE users;

    SQL Server (T-SQL) equivalents:
    SELECT * FROM INFORMATION_SCHEMA.TABLES;
    SELECT name FROM sys.databases;
    SELECT * FROM sys.indexes WHERE object_id = OBJECT_ID('users');
    SELECT * FROM sys.procedures;
    -- No direct SHOW commands; use system catalog views instead.

-------------------------------------------------------
12. DELIMITER
-------------------------------------------------------

    MySQL:
    -- Needs DELIMITER change for stored procedures (as covered in notes)
    DELIMITER $$
    ...
    END $$
    DELIMITER ;

    SQL Server (T-SQL):
    -- No DELIMITER concept. Uses GO as a batch separator instead.
    -- GO is not a T-SQL command, it is an SSMS instruction.
    SELECT * FROM users;
    GO
    SELECT * FROM orders;
    GO

-------------------------------------------------------
13. ISNULL / IFNULL / COALESCE
-------------------------------------------------------

    MySQL:
    SELECT IFNULL(salary, 0) FROM users;
    -- Returns 0 if salary is NULL

    SQL Server (T-SQL):
    SELECT ISNULL(salary, 0) FROM users;
    -- Same behaviour, different function name

    Both support COALESCE (ANSI standard, works in both):
    SELECT COALESCE(salary, 0) FROM users;
    -- Preferred if writing code that might run on both databases.

=======================================================
WHAT IS THE SAME IN BOTH (no change needed)
=======================================================

    These work identically in MySQL and SQL Server:
        SELECT, FROM, WHERE, ORDER BY, GROUP BY, HAVING
        INSERT INTO, UPDATE SET, DELETE FROM
        INNER JOIN, LEFT JOIN, RIGHT JOIN
        COUNT(), SUM(), AVG(), MIN(), MAX()
        ROUND(), FLOOR(), CEIL()
        CASE WHEN ... THEN ... ELSE ... END
        COALESCE()
        IS NULL, IS NOT NULL
        AND, OR, NOT, IN, NOT IN, BETWEEN, LIKE
        PRIMARY KEY, FOREIGN KEY, UNIQUE, NOT NULL, DEFAULT
        CREATE TABLE, ALTER TABLE, DROP TABLE
        Transactions: BEGIN TRANSACTION / COMMIT / ROLLBACK
        VIEWS: CREATE VIEW, DROP VIEW

    The core SQL you have been learning applies to BOTH databases.
    The differences are mostly in function names and a few keywords.

GROUP BY — HOW IT WORKS BEHIND THE SCENE
========================================================


THE GOLDEN RULE
---------------
SQL does NOT run top to bottom.
This is the actual execution order:

   1. FROM + JOIN   → bring tables together
   2. WHERE         → filter individual rows
   3. GROUP BY      → separate rows into buckets/piles
   4. HAVING        → filter the buckets/piles
   5. SELECT        → pick what to display
   6. ORDER BY      → sort final result


--------------------------------------------------------
THE BUCKET SYSTEM — REAL EXAMPLE
--------------------------------------------------------

QUERY:
   SELECT u.name, COUNT(*) AS login_count
   FROM users u
   INNER JOIN user_log ul ON u.id = ul.user_id
   WHERE ul.name = 'Login'
   GROUP BY u.name;


YOUR TWO TABLES:

   users                    user_log
   ------                   --------
   id   name                user_id   action
   1    Ujjwal              1         Login
   2    Raj                 1         Login
   3    Meera               1         Logout
                            2         Login
                            2         Logout
                            3         Login
                            3         Login
                            3         Login


STEP 1 — FROM + JOIN
Combine both tables where users.id = user_log.user_id:

   u.name    ul.action
   Ujjwal    Login
   Ujjwal    Login
   Ujjwal    Logout
   Raj       Login
   Raj       Logout
   Meera     Login
   Meera     Login
   Meera     Login

   All 8 rows present. Nothing removed yet.


STEP 2 — WHERE ul.action = 'Login'
Remove any row that is not Login:

   u.name    ul.action
   Ujjwal    Login      ✔ kept
   Ujjwal    Login      ✔ kept
   Ujjwal    Logout     ✘ removed
   Raj       Login      ✔ kept
   Raj       Logout     ✘ removed
   Meera     Login      ✔ kept
   Meera     Login      ✔ kept
   Meera     Login      ✔ kept

   Remaining rows:
   Ujjwal / Raj / Meera Login rows only.


STEP 3 — GROUP BY u.name
Separate remaining rows into piles, one pile per unique name:

   Ujjwal pile     Raj pile     Meera pile
   -----------     --------     ----------
   Login           Login        Login
   Login                        Login
                                Login


STEP 4 — COUNT(*)
Count how many rows are in each pile:

   Ujjwal pile  →  2
   Raj pile     →  1
   Meera pile   →  3

   IMPORTANT: COUNT does NOT know or care about months, names,
   or any grouping logic. It just counts rows in whatever pile
   GROUP BY created. GROUP BY makes the piles. COUNT counts them.


STEP 5 — SELECT
Show u.name and the count:

   name      login_count
   Ujjwal    2
   Raj       1
   Meera     3


--------------------------------------------------------
WHERE vs HAVING — THE KEY DIFFERENCE
--------------------------------------------------------

WHERE   →  filters ROWS before grouping (faster)
HAVING  →  filters GROUPS/PILES after grouping

Use WHERE when condition is on a raw column.
Use HAVING when condition is on an aggregate (COUNT, AVG, SUM etc.)

   -- Show states with more than 3 users
   SELECT state, COUNT(*) AS total_users
   FROM users u
   INNER JOIN addresses a ON u.id = a.user_id
   GROUP BY state
   HAVING COUNT(*) > 3;

   Behind the scene:
   - GROUP BY separates rows into state piles
   - COUNT(*) counts each pile
   - HAVING then removes piles where count is 3 or less
   - Only piles with more than 3 survive


--------------------------------------------------------
COUNT(*) vs COUNT(column) — IMPORTANT DIFFERENCE
--------------------------------------------------------

COUNT(*)         →  counts ALL rows including NULLs
COUNT(a.user_id) →  skips NULLs

When to use COUNT(column):
   When you want users with ZERO matches to show as 0, not 1.

   Example — count addresses per user including users with no address:

   SELECT u.name, COUNT(a.user_id) AS address_count
   FROM users u
   LEFT JOIN addresses a ON u.id = a.user_id
   GROUP BY u.name;

   After LEFT JOIN, users with no address get NULL in address columns.
   COUNT(*)         counts that NULL row → gives 1 (WRONG)
   COUNT(a.user_id) skips that NULL      → gives 0 (CORRECT)


--------------------------------------------------------
QUICK MENTAL CHECKLIST FOR EVERY GROUP BY QUERY
--------------------------------------------------------

1. What tables do I need?              → FROM + JOIN
2. Do I need to remove any rows?       → WHERE
3. What do I want to group by?         → GROUP BY
4. What do I want to count/sum/avg?    → COUNT / SUM / AVG
5. Do I need to filter the groups?     → HAVING
6. What columns do I want to see?      → SELECT
